# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant e-commerce platform (Payload CMS 3 + Next.js 15 App Router). Each tenant is a "store" (e.g. `sellroad.shop` style branding, though tenants currently route by path, not subdomain — see Routing below). Sellers register, get a tenant + Stripe Connect account, list products, and buyers check out per-tenant carts via Stripe Checkout.

## Commands

Package manager is **bun** (see `bun.lock`, `bunx` usage in scripts).

- `bun run dev` — runs the Next.js dev server AND an SSL proxy concurrently (proxy forwards `3002` → `3000`, needed for local HTTPS/Stripe webhook testing)
- `bun run next-dev` — Next.js dev server only (port 3000)
- `bun run build` — production build (runs `withPayload`-wrapped Next build)
- `bun run start` — start production server
- `bun run lint` — `next lint`
- `bun run payload:types` — regenerate `src/payload-types.ts` from collection configs (run this after editing anything in `src/collections/`)
- `bun run payload:migrate:fresh` — drop and recreate the database schema/migrations
- `bun run db:seed` — run `src/seed.ts` to seed the database

There is no test runner configured in this repo.

### Payload admin & API

- Admin UI: `/admin` (route group `src/app/(payload)`)
- REST/GraphQL API generated by Payload: `src/app/(payload)/api/`
- tRPC API: `src/app/api/trpc/[trpc]/route.ts`
- Stripe webhook endpoint: `src/app/api/stripe/webhooks/route.ts` (use the SSL proxy or `stripe listen` for local testing — a `stripe` binary/tarball is vendored at the repo root)

## Architecture

### Payload CMS as the backend

`src/payload.config.ts` is the single source of truth for the data layer: collections, auth, plugins, i18n (`en`/`ar`). MongoDB via `@payloadcms/db-mongodb`. Collections live in `src/collections/`: `Users`, `Media`, `Categories`, `Products`, `Tags`, `Tenants`, `Orders`, `Reviews`.

`src/payload-types.ts` is **generated** — never hand-edit it; run `bun run payload:types` after changing a collection.

### Multi-tenancy (`@payloadcms/plugin-multi-tenant`)

This is the architectural core of the app — read `MULTITENANT.md` for the original design notes. Key points:

- The plugin auto-injects a hidden `tenant` relationship field into collections listed under `collections: { products: {} }` in `payload.config.ts`, and auto-filters reads/writes to the active tenant.
- `Users` is **not** in the plugin's `collections` list (`includeDefaultField: false`); instead `defaultTenantArrayField` (from `@payloadcms/plugin-multi-tenant/fields`) is manually spread into `src/collections/Users.ts` so the array field can be placed in the sidebar and given custom access control.
- `userHasAccessToAllTenants` grants global access to users with the `super-admin` role (see `roles` field on `Users`).
- On registration (`src/modules/auth/server/procedures.ts`), a new `tenants` doc is created per user (tenant slug = username) along with a placeholder `stripeAccountId: "test"` — every user is a potential seller.

### Routing structure (`src/app/(app)/...`)

Route groups separate concerns, all still same-origin (no subdomain middleware exists):

- `(home)` — main marketplace: category/subcategory browsing at `[category]/[subcategory]`, static pages (about/pricing/contact/features)
- `(tenants)/tenants/[slug]` — a single tenant's storefront, itself split into:
  - `(home)` — tenant landing + `products/[productId]`
  - `(checkout)/checkout` — tenant-scoped checkout page
- `(library)/library` — the buyer's purchased-products library (`[productId]` = a single owned product + reviews)
- `(auth)` — sign-in / sign-up
- `(payload)` — Payload's own admin/API route group, kept separate from the storefront layout

Each `[slug]`/tenant layout calls `trpc.tenants.getOne` to resolve/validate the tenant before rendering.

### Feature modules (`src/modules/*`)

Business logic is organized by domain, not by framework layer. Each module typically contains:

```
modules/<domain>/
  server/procedures.ts   # tRPC router for this domain
  ui/views/               # top-level page components (composed into app/ routes)
  ui/components/          # domain-specific components
  hooks/                  # domain-specific React hooks
  schemas.ts / types.ts   # zod schemas / shared types
```

Modules: `auth`, `categories`, `checkout`, `home`, `library`, `products`, `reviews`, `tags`, `tenants`. App router pages stay thin — they mostly prefetch tRPC data and render a view from the corresponding module.

### tRPC setup (`src/trpc/`)

- `init.ts` defines `baseProcedure` (attaches `ctx.db` = a Payload instance) and `protectedProcedure` (also validates the session via `ctx.db.auth({ headers })` and throws `UNAUTHORIZED` if no user — after this, `ctx.session.user` is safely non-nullable).
- `routers/_app.ts` combines all per-module routers into `appRouter`; add new domain routers there.
- `server.tsx` exposes server-side helpers: `trpc` (query options proxy), `prefetch()`, `HydrateClient`, and `caller` (direct server-side invocation without HTTP).
- `client.tsx` is the client-side React Query + tRPC provider.
- Pattern used throughout: a Server Component calls `prefetch(trpc.x.y.queryOptions(...))`, wraps children in `<HydrateClient>`, and a Client Component further down calls `useSuspenseQuery(trpc.x.y.queryOptions(...))` to read the already-hydrated data.

### Checkout & payments (Stripe Connect)

- Cart state is client-only: `zustand` store (`src/modules/checkout/store/use-cart-store.ts`) persisted to `localStorage`, keyed **per tenant slug** (`tenantCarts: Record<tenantSlug, { productIds }>`) since a cart can only contain one tenant's products at checkout time.
- `checkoutRouter.purchase` (protected) re-fetches products server-side by ID _and_ tenant slug to prevent client-side price/tenant tampering, then creates a Stripe Checkout Session with `metadata.stripeAccountId` per line item (Stripe Connect destination charges pattern).
- `checkoutRouter.getProducts` (public) resolves cart product IDs to full product docs + computed `totalPrice` for rendering the cart sidebar.
- Successful purchases are expected to be recorded into the `Orders` collection via the Stripe webhook handler (`src/app/api/stripe/webhooks/route.ts`), linking `user` + `product` + `stripeCheckoutSessionId`.

### Library & reviews (post-purchase)

The `library` module is the buyer's "my purchases" area — it does **not** trust the product collection directly; `library.getOne`/`getMany` first verify an `Orders` doc exists for `(product, user)` before returning product data. This is the ownership-gate pattern for any future "only if purchased" feature (e.g. leaving a review).

### Path aliases

`@/*` → `src/*`, `@payload-config` → `src/payload.config.ts` (used by Payload internals and `getPayload({ config })` calls). Defined in `tsconfig.json`.

## Environment variables

Required (see `.env.example` and `.env` keys, not committed values): `DATABASE_URI`, `PAYLOAD_SECRET`, `NEXT_PUBLIC_APP_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`.

## Conventions observed in this codebase

- i18n: collection labels are bilingual (`en`/`ar`) objects — follow this pattern when adding fields/labels to collections.
- Server-only trust boundary: any procedure that touches money, ownership, or tenant scoping re-validates against the database rather than trusting client-supplied IDs/prices (see `checkout` and `library` procedures above) — follow this when adding similar procedures.
- UI primitives come from shadcn/ui (`components.json`: style `new-york`, base color `neutral`, icon library `lucide`) — generate/add new primitives with the shadcn CLI rather than hand-rolling them, and place them under `src/components/ui`.
